# ADR-019.1 — `AI_COMPLIANCE_MODE` Env Toggle (Sidecar) + Production Safety

- **Status**: Accepted (svc-viability-v4 W4, 2026-05-25). Implemented via V077 (`ai_compliance_mock_used` action_code INSERT) + `services/marketing/core.py::_MOCK_EMIT_STATE` singleton + own-asyncpg `_emit_mock_singleton` helper + `main.py` startup `RuntimeError` guard against `app_env == "production"`. W3 commit. `.env.example` carries the 4-line operator note.
- **Predecessor**: svc-viability-v3 mid-cycle finding F8 — `services/marketing/core.py::ai_compliance_check` fail-closes whenever Azure OpenAI is unavailable, which in PoC means the marketing 4-eye preventive gate downstream cannot be exercised through the normal HTTP path. - **Cycle**: svc-viability-v4 (ralplan iter-2 APPROVE)
- **Relationship to ADR-019**: this is a **sidecar** that unblocks the marketing-side path to PENDING_APPROVAL. The state machine itself lives in ADR-019.
- **Relationship to ADR-002**: ADR-002 covers email authority + schema contract. The AI compliance mode toggle is **out of scope** for ADR-002; conflating the two would muddy the email authority decision history. Hence the sidecar.

## Context

`services/marketing/core.py:230-285` defines `ai_compliance_check(subject, body, pre_review_number)`:

```python
async def ai_compliance_check(subject, body, pre_review_number):
    endpoint = os.getenv("AZURE_OPENAI_ENDPOINT", "").strip()
    api_key = os.getenv("AZURE_OPENAI_API_KEY", "").strip()
    deployment = os.getenv("AZURE_OPENAI_DEPLOYMENT_NAME", "").strip()
    if not (endpoint and api_key and deployment):
        return AiComplianceResult(passed=False, issue_codes=["AI_UNAVAILABLE"], ...)
    try:
        ...
    except Exception as exc:
        return AiComplianceResult(passed=False, issue_codes=["AI_ERROR"], ...)
```

In production this is correct: an unreachable LLM should fail-closed. In the PoC environment we cannot exercise the 4-eye gate downstream because the marketing draft submission rejects before reaching the 4-eye branch. v3 verified the 4-eye row only by direct DB INSERT into PENDING_APPROVAL, which is not how regulators or auditors would exercise the gate.

We need a runtime toggle that:
1. Defaults to `live` (current behavior).
2. Refuses to start in production with any other mode.
3. Emits an auditable signal exactly once per process when a non-`live` mode is used.
4. Logs a WARNING so on-call alerts surface the toggle even if the audit ledger is missed.

## Decision

### Env variable

```
AI_COMPLIANCE_MODE=<live|mock_pass|mock_fail>   # default: live
```

- `live` — current production behavior (Azure call + fail-closed on error).
- `mock_pass` — return `AiComplianceResult(passed=True, ..., ai_called=False)` without touching Azure.
- `mock_fail` — return `AiComplianceResult(passed=False, issue_codes=["MOCK_FAIL"], ...)` without touching Azure.

Any value other than the three above raises `ValueError` at the call site.

### Singleton audit emit (`ai_compliance_mock_used`)

`services/marketing/core.py` adds a module-level state dict:

```python
_MOCK_EMIT_STATE: dict[str, Any] = {"emitted": False, "mode_first_seen_at": None}
```

The first non-`live` invocation per process:

1. Sets `_MOCK_EMIT_STATE["emitted"] = True` and `mode_first_seen_at` to the current ISO timestamp.
2. Inserts an `audit_logs` row with `action_code='ai_compliance_mock_used'`, `resource_type=NULL`, `resource_id=NULL`, `detail={"mode": "mock_pass"|"mock_fail", "pid": os.getpid(), "started_at": iso, "mode_first_seen_at": iso}`.
3. Emits `logger.warning("ai_compliance_mock_used singleton emit: mode=%s pid=%d started_at=%s", ...)`.

Subsequent invocations of any non-`live` mode within the same process do **not** emit. The cardinality contract is "exactly 1 audit row per process, regardless of N follow-up invocations".

This singleton design is the OQ-V4-CR1 lock (`audit_logs + WARNING log both`): the audit ledger carries the durable evidence; the WARNING gives an immediate ops alert without inflating audit row count.

### Production safety check

`main.py` startup (or `core/config.py` post-load):

```python
def _validate_ai_compliance_mode(settings: RuntimeConfig) -> None:
    ai_mode = os.getenv("AI_COMPLIANCE_MODE", "live").strip()
    if ai_mode != "live" and settings.app_env == "production":
        raise RuntimeError(
            f"AI_COMPLIANCE_MODE must be 'live' in production "
            f"(app_env={settings.app_env}, got mode={ai_mode})"
        )
```

The access pattern is `startup_config.runtime.app_env == "production"` — **not** `ENVIRONMENT == "production"` and **not** `settings.app_env` (the latter was the planner-iter-2 access pattern; actual `main.py` reads through `AppConfig.runtime: RuntimeConfig`, see Evidence below). Evidence:

- `apps/api/harness/core/config.py:37-38` — `class RuntimeConfig` with `app_env: str` field.
- `apps/api/harness/core/config.py:100-101` — `class AppConfig` with `runtime: RuntimeConfig` field.
- `apps/api/harness/core/config.py:330` — `app_env=require_env("APP_ENV")` populates `RuntimeConfig`.
- `apps/api/harness/main.py:39-46` — actual startup check uses `startup_config.runtime.app_env`.
- `.env:104` — `APP_ENV=development` (default).

The check fires at FastAPI startup, before any request can land. The process refuses to come up if the combination is wrong, which makes a misconfigured deploy fail loudly instead of leaking mock approvals through the 4-eye gate.

### Layered protection

```
Layer 1 — env discipline + .env.example comment
Layer 2 — startup RuntimeError (process refuses to start)
Layer 3 — singleton audit_logs row (audit ledger evidence)
Layer 4 — logger.warning (on-call alert path)
```

A single layer failing does not produce a silent production mock. Layer 2 alone catches the most common misconfiguration. Layer 3 catches the case where Layer 2 is bypassed by ad-hoc env injection at process start. Layer 4 catches the case where audit ledger sinks are queue-buffered and slow.

## Drivers

1. **PoC verifiability (Driver 1)** — the 4-eye preventive control at `routers/consultations.py:update_consultation` (ADR-019) is only meaningfully exercisable end-to-end if marketing draft submission can reach the PENDING_APPROVAL state. The mock unblocks that path without lying to production.
2. **Fail-loudly in production (Driver 2)** — every mitigation layer raises rather than swallows. There is no "log and continue" fallback that could mask a misconfigured deploy.
3. **Single SoT for env sentinel (Driver 3)** — Input-1 corrected the access pattern across plan + ADR + main.py + .env.example to `settings.app_env`. Future env additions must follow the same pattern (RuntimeConfig field + `require_env(...)` + `.env.example` line).

## Alternatives Considered

### Option-B (REJECTED, confidence 0.95) — pytest monkeypatch only

Use `monkeypatch.setattr(services.marketing.core, "ai_compliance_check", ...)` in tests.

Rejected because:
- It does not exercise the live HTTP path. The 4-eye gate at `routers/consultations.py` would be tested through a unit-level fake instead of the real router.
- It would not produce a real `audit_logs` row, so the cardinality contract for `four_eyes_violation_blocked` cannot be verified fresh from psql.
- The PoC needs to be exercised by humans (regulators, auditors, security reviewers) without a Python testing harness in front of them.

### Option-C (REJECTED, confidence 0.80) — Azure OpenAI emulator

Stand up a local emulator that always returns `passed=True`.

Rejected because:
- Adds an external service to the dev loop with its own deploy and maintenance overhead.
- The PoC explicitly forbids docker for hosted services (per project policy).
- We do not need to test Azure's actual response shape; we need to bypass the unavailability of Azure in this environment.

### Option-D (REJECTED, confidence 0.85) — Per-invocation audit emit

Emit `ai_compliance_mock_used` on every non-`live` call.

Rejected because:
- Inflates `audit_logs` row count under load tests.
- Loses the "this process started in mock mode" signal in noise — investigators want the first emit timestamp, not the 1000th.
- The singleton design preserves the evidence with O(1) row count per process.

## Consequences

### Positive

- PoC can demonstrate the 4-eye preventive gate end-to-end: marketing draft → submit (200, AI mock_pass) → consultation PENDING_APPROVAL → self-approve attempt (403 + `four_eyes_violation_blocked` row).
- Production cannot start with a non-`live` mode (Layer 2 RuntimeError).
- A non-`live` startup leaves a single audit row + WARNING log per process, recoverable from the ledger even months later.

### Negative

- Adds a runtime env variable to the deploy contract. `.env.example` must comment the constraint explicitly to avoid foot-guns.
- Audit row count contract ("exactly 1 per process") must be defended by the test in `tests/test_marketing_core_mock_mode.py` — if a future refactor moves the singleton state outside `_MOCK_EMIT_STATE`, the contract silently breaks.

### Risks

- **R3** Production leak — mitigated by 4-layer (env + startup + audit + WARNING). Pre-mortem Scenario-2.
- **F-V5-7** Audit alert query (`SELECT ... WHERE action_code='ai_compliance_mock_used'`) is the long-term safety net once production runs.

## Follow-ups

- **F-V5-4** Frontend toggle UI for the mock mode (developer-facing only). Backend env is canonical.
- **F-V5-7** Production alert on any `ai_compliance_mock_used` row in `audit_logs` (the row should not exist in production at all).
