# ADR-018 — `house_views` ADMIN-only Cross-Admin Regeneration Audit

- **Status**: Accepted (svc-viability-v4 W4, 2026-05-25). Implemented via V074 (`house_view_regenerated_by_admin` action_code INSERT, schema change 0) + `GET_PREVIOUS_HOUSE_VIEW_GENERATOR_SQL` (ai_jobs SoT, OFFSET 1 LIMIT 1) + transaction-wrapped emit at `routers/house_views.py:generate_house_view` (W1 commit). CANONICAL tuple registration in `apps/api/harness/core/audit.py` (W1/W2 sync).
- **Predecessor**: svc-viability-v3 closure handoff §4 follow-up row 2 — `house_view_regenerated_by_admin` was flagged separately from the 4-eye same-actor invariant because `routers/house_views.py` is ADMIN-only and the invariant semantic is "cross-admin regeneration observability", not "two-person rule".
- **Cycle**: svc-viability-v4 (ralplan iter-2 APPROVE)
- **Plan SoT**: `<repo-root>/.omc/plans/ralplan-wmah-service-viability-v4.md` §4 I2 + §11.

## Context

`house_views` is an ADMIN-only resource: only the `ADMIN` role can call `POST /house-views/{house_view_id}/generate`. The 4-eye preventive gate (different person approves) is meaningless here because the endpoint already gates writes to a single role family. The remaining auditable event is **which admin regenerated a house view that another admin last generated**.

The challenge is that no row on `house_views` records the "last generator". `V004__house_views.sql:12` defines `created_by_id UUID NOT NULL REFERENCES employees(id)` but that is the **creator-at-DRAFT** — it never updates after subsequent regenerations. The current router (`routers/house_views.py:120-154`) inserts an `ai_jobs` row for each generate request, which IS the per-generation actor record.

Adding a `last_generated_by_actor_id` column to `house_views` would duplicate `ai_jobs.requested_by_id` and introduce a dual SoT. Instead, we use the `ai_jobs` table directly as the natural SoT and look up the *previous* generator with a deterministic SQL query.

## Decision

Use **Option-A (`ai_jobs` SQL lookup, schema change 0)** plus a new action code in V074:

### V074 — `house_view_regenerated_by_admin` action code

```sql
/* sql_id: v074_house_view_regenerated_action_code */
INSERT INTO audit_action_codes (action_code, description)
VALUES ('house_view_regenerated_by_admin',
        'ADMIN regenerated a house_view that was last generated by a different ADMIN')
ON CONFLICT (action_code) DO NOTHING;
```

No `ALTER TABLE` is needed. The action code is also added to `apps/api/harness/core/audit.py::CANONICAL_AUDIT_ACTION_CODES` to satisfy the two-source registration rule (I8 contract test).

### Lookup SQL — previous generator

```sql
/* sql_id: get_previous_house_view_generator */
SELECT requested_by_id
FROM ai_jobs
WHERE job_type_code = 'house_view_generation'
  AND resource_id = $1::uuid
ORDER BY created_at DESC
OFFSET 1
LIMIT 1;
```

- `OFFSET 1 LIMIT 1` returns the **immediately prior** generation row. The current generation lives at `OFFSET 0` because the router already inserted it before this lookup runs.
- First-ever generation returns zero rows; the router treats this as `previous=None` and skips the emit.
- The query is executed inside the same `connection.transaction()` block as the `ai_jobs` insert + audit emit, so the visibility ordering is well-defined (`READ COMMITTED` sees the previous row but not the current INSERT after the same-transaction sequence — confirmed by Architect iter-2 review).

### Router emit semantics

```python
# routers/house_views.py generate_house_view (Input-5 transaction wrap)
async with get_pool(request).acquire() as connection:
    async with connection.transaction():
        job = await ai_repo.create_ai_job(
            connection,
            job_type_code="house_view_generation",
            requested_by_id=actor.employee_id,
            resource_type="house_view",
            resource_id=house_view_id_text,
        )
        await audit_repo.insert_audit_log(
            connection, ..., action_code="AI_CALL_STARTED", ...,
        )

        previous_row = await connection.fetchrow(
            GET_PREVIOUS_HOUSE_VIEW_GENERATOR_SQL, house_view_id_text,
        )
        previous_actor_id = previous_row["requested_by_id"] if previous_row else None

        if previous_actor_id is not None and not same_actor(
            actor.employee_id, previous_actor_id
        ):
            await audit_repo.insert_audit_log(
                connection,
                actor_id=actor.employee_id,
                action_code="house_view_regenerated_by_admin",
                resource_type="house_view",
                resource_id=house_view_id_text,
                detail={
                    "previous_generated_by_actor_id": str(previous_actor_id),
                    "current_actor_id": str(actor.employee_id),
                    "ai_job_id": str(job["id"]),
                },
                **request_audit_context(request),
            )
```

### Semantic differentiation from `same_actor_mutation_blocked`

| Action code | Trigger condition | Invariant |
|---|---|---|
| `same_actor_mutation_blocked` | actor == previous actor on a mutation | "the same person should not mutate twice in a row" (multi-role) |
| `house_view_regenerated_by_admin` | actor != previous actor on a regeneration (single-role, ADMIN) | "regenerations crossed admin boundary — record who handed off to whom" |

Keeping the action codes distinct avoids cross-contaminating the 4-eye semantic with cross-admin observability. The Layer-4 row in `docs/observability/OBS-02_audit_action_codes.md` (I5 batch update) lists the emit source as `routers/house_views.py:generate_house_view` with `resource_type=house_view`.

## Drivers

1. **`ai_jobs` is the natural SoT (Driver 1)** — every generate request inserts an `ai_jobs` row with `requested_by_id=actor.employee_id`. The previous generator is one query away. Adding a duplicate column on `house_views` would force the router to keep both stores consistent on every generation.
2. **Schema change zero (Driver 2)** — V074 is INSERT-only, no `ALTER TABLE`. `house_views` and `ai_jobs` row counts are unchanged. v3 audit_v1 regression risk is bounded to "the new audit emit fires when expected".
3. **Semantic clarity (Driver 3)** — the cross-admin invariant is observability, not preventive control. A separate action code keeps OBS-02 row meta_keys interpretable (`previous_generated_by_actor_id` + `current_actor_id` + `ai_job_id`, per Input-11 per-resource_type meta_keys variation).

## Alternatives Considered

### Option-B (REJECTED, confidence 0.80) — `house_views.last_generated_by_actor_id`

Add `last_generated_by_actor_id UUID REFERENCES employees(id) DEFAULT NULL` on `house_views`.

Rejected because:
- Duplicates `ai_jobs.requested_by_id` — every generation must write both, and on rollback both must be unwound consistently.
- Schema bloat: a new nullable column with FK plus the index to keep the same-actor compare cheap.
- `ai_jobs` already records the per-request actor with full timestamp/status context; the column would only restate it.

### Option-C (REJECTED, confidence 0.70) — Reuse `same_actor_mutation_blocked` (semantic conflation)

Reject reusing the 4-eye action code for ADMIN cross-admin regen.

Rejected because:
- The 4-eye action code is registered for **preventive** + **detective** controls on multi-role mutation paths. ADMIN single-role regen is neither preventive nor a violation — it is an observability ledger.
- OBS-02 readers must already interpret `same_actor_mutation_blocked` across three distinct resource types (`consultation`, `kyc_edd_trigger`, `dispute_case`). Adding a fourth resource type with reversed semantics ("emit when actor != previous", not "emit when actor == previous") would break the action-code-to-invariant contract.

## Consequences

### Positive

- Zero `house_views` row mutations. Existing V004 / V008 audit_v1 fixtures stay valid.
- OBS-02 row carries fully-typed meta_keys with the `ai_job_id` correlation handle so investigators can pivot directly to the job ledger.
- Cross-admin observability lives on the audit ledger only, with append-only semantics. There is no mutable derived column to keep consistent with `ai_jobs`.

### Negative

- Every generate request runs one extra `SELECT` against `ai_jobs`. The query is indexed on `(job_type_code, resource_id, created_at)` (already present in V008). Latency impact under load is bounded by the same index v3 already relies on.
- The previous-actor lookup is "the prior `ai_jobs` row with `job_type_code='house_view_generation'`". A non-generation job (e.g., a draft preview) cannot appear in the same lane. If future job types are added that share `resource_type=house_view`, the filter must be revisited (F-V5-7 lint hint).

### Risks

- **R3** Audit emit cardinality drift if router transaction fails between `create_ai_job` and the previous-actor query — mitigated by the `async with connection.transaction():` wrap (Input-5).

## Follow-ups

- **F-V5-1** Frontend display of `house_view_regenerated_by_admin` events on the audit ledger UI. Backend emit is canonical; UI surfacing is deferred to v5.
- **F-V5-7** Production alert / dashboard query: `SELECT COUNT(*) FROM audit_logs WHERE action_code='house_view_regenerated_by_admin' AND created_at > now() - interval '1 hour'`. Treat sudden spikes as cross-admin coordination signal.
